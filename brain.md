# 4. Core Product Philosophy

## Evidence Before Trust

> **Don't ask users to blindly trust AI. Give them the evidence required to understand and verify the intelligence.**

Important financial claims should, where technically and legally possible, be traceable to:

```text
CLAIM
  ↓
SOURCE
  ↓
EVIDENCE
  ↓
TIMESTAMP
  ↓
CALCULATION / METHODOLOGY
  ↓
CONFIDENCE / UNCERTAINTY
```

The user should be able to understand:

* what QuantMind is saying
* why it is saying it
* what evidence supports the statement
* when the evidence was produced
* what calculations were performed
* what uncertainty exists

Trust should come from transparency and verification, not from the AI simply sounding confident.

# 18. AI Behavior Rules

All AI systems operating inside QuantMind must follow these principles.

## 18.1 Never Invent Financial Facts

Do not fabricate:

* prices
* financial metrics
* earnings numbers
* company events
* analyst estimates
* sources
* filings
* dates
* market data
* calculations

If information is unavailable, say so.

---

## 18.2 Separate Facts From Interpretation

QuantMind should distinguish between:

### FACT

Information directly supported by available data or sources.

### CALCULATION

A mathematically derived result.

### INTERPRETATION

An AI-generated explanation based on available evidence.

### HYPOTHESIS

A possible explanation that requires further verification.

### UNCERTAINTY

Information for which evidence is incomplete, conflicting, or insufficient.

These categories must not be presented as equivalent.

# 19. Temporal Correctness

Financial information changes over time.

QuantMind must respect the time dimension of data.

For historical research:

```text
Historical Question
       ↓
Information Available At That Time
       ↓
```

This is particularly important for:

* backtesting
* historical research
* strategy evaluation
* event studies
* financial simulations

# 28. Scope-Control Rule

Before implementing a new feature, determine:

1. Is it required for NOW?
2. Is it defined in the PRD?
3. Is it inside MVP-Scope?
4. Does it require new infrastructure?
5. Does it require new financial data?
6. Does it introduce regulatory complexity?
7. Does it change the architecture?
8. Does it depend on a future roadmap capability?

If a feature belongs to NEXT or VISION, it should normally be deferred.

# 30. Current Assumptions

The project currently assumes:

1. Financial research is an appropriate initial product wedge.
2. Evidence-backed AI can provide more useful financial intelligence than unsupported AI-generated conclusions.
3. Reliable financial data infrastructure is foundational.
4. Quantitative computation should be separated from LLM reasoning where practical.
5. Explainability should be built into the architecture rather than added later.
6. The first product should be substantially narrower than the long-term platform.
7. Professional financial workflows and personal financial intelligence may eventually share the same underlying intelligence infrastructure.
8. Data licensing and regulatory considerations must be treated as product architecture concerns.
9. Real user validation is necessary before major expansion.
10. The long-term platform should evolve from a proven core rather than attempting to build every capability simultaneously.

These are **assumptions**, not proven facts.

They should be revisited as evidence changes.

# 35. Decision-Making Framework

When evaluating a major product or architecture proposal, ask:

* What user problem does this solve?
* Who needs it?
* Is it NOW, NEXT, or VISION?

## Evidence

* What validates the need?
* What evidence supports the assumption?

## Data

* What data does it require?
* Is that data legally and technically accessible?
* How fresh must it be?

## AI

* Does AI genuinely add value?
* What can go wrong?
* How will the output be evaluated?

## Quant

* Are calculations required?
* Can they be independently validated?

## Security

* Does the feature involve sensitive financial information?

## Regulation

* Could the feature constitute a regulated financial activity?

## Architecture

* Does it introduce unnecessary complexity?
* Does it create avoidable vendor lock-in?

## Scope

* Does it actually belong in the current phase?
